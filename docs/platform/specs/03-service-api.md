# Spec 03: Service API

Milestone M2 (and M6, M7 additions). Depends on specs 01 and 02.

## Purpose

One HTTP service that stores documents, starts simulation and optimisation jobs, and serves
results and the web app. It contains no simulation logic of its own.

## Stack

- Python package `service/` (not `platform/`: that name shadows a standard-library module).
- FastAPI + uvicorn + pydantic (new dependencies, in `requirements.txt`).
- SQLite through the standard library for metadata; large blobs as gzip JSON files under
  `data/` (path from `PATHWAY_DATA_DIR`). Postgres only if we outgrow one container.
- Jobs: a `ProcessPoolExecutor` owned by the service; job rows in SQLite.
- The API description (OpenAPI) is generated by FastAPI at `/docs`; the web app's types are
  generated from it.

## Resources

All under `/api`. `{p}` is a project id.

| Method and path | Purpose |
|---|---|
| `GET /templates` | Built-in worlds and flowcharts (Norway check, Finnish scenario), converted from the YAML at start-up |
| `POST /projects` `{name, template?}` | New project, optionally copied from a template |
| `GET /projects`, `GET /projects/{p}`, `DELETE /projects/{p}` | |
| `GET/PUT /projects/{p}/world` | The world document; `PUT` validates |
| `GET /projects/{p}/flowcharts` | Flowcharts with their latest version |
| `POST /projects/{p}/flowcharts` | New flowchart (version 1) |
| `GET /projects/{p}/flowcharts/{f}/versions/{v}` | One immutable version |
| `POST /projects/{p}/flowcharts/{f}/versions` | Save a new version (body: document; `parent_version` set by the server) |
| `POST /projects/{p}/validate` `{world?, flowchart}` | Problem list (spec 01); never stores |
| `POST /projects/{p}/decide` `{flowchart, decision_point, context}` | "Try a decision": probabilities from the flowchart's decision policy for one hand-entered context |
| `POST /projects/{p}/runs` | Start a run (below) |
| `GET /projects/{p}/runs`, `GET /projects/{p}/runs/{r}` | List; status, progress, metrics |
| `GET /projects/{p}/runs/{r}/bundle` | Result in the dashboard bundle format (`demo/README.md`) |
| `GET /projects/{p}/runs/{r}/decisions` | Every decision in the run as dataset rows (spec 06), JSON lines |
| `GET /projects/{p}/runs/{r}/patients?offset&limit` | Patient-level log, paged |
| `POST /projects/{p}/compare` `{runs: [a, b]}` | Metric deltas; refuses runs on different patients |
| `POST /projects/{p}/optimisations` | Start an optimisation (spec 05) |
| `GET /projects/{p}/optimisations/{o}` | Status; suggested changes, evidence, before and after |
| `POST /projects/{p}/optimisations/{o}/apply` `{accept: [0, 2]}` | New flowchart version from the accepted changes |
| `POST /projects/{p}/datasets`, `GET …/datasets/{d}` | Upload; validation report (spec 06) |
| `POST /projects/{p}/models`, `GET …/models/{m}` | Train; registry entry (spec 06) |
| `GET /jobs/{j}`, `POST /jobs/{j}/cancel` | Any job's status, progress, log tail |

### Starting a run

```json
POST /api/projects/{p}/runs
{"flowchart": {"id": "baseline", "version": 3},
 "n": 18800, "seeds": [301, 302],
 "decision_policy": null,
 "label": "after first two changes"}
→ 202 {"run_id": "r_8f2c", "job_id": "j_41", "status": "queued"}
```
`decision_policy: null` means "use the one stored in the flowchart version"; a value overrides it
for this run, which is how "same flowchart, stub versus JEV" is compared.

A run is identified by a hash of (world, flowchart version, decision policy, n, seeds, engine
version). An identical request returns the existing run instead of recomputing.

Stored per run: metrics (per seed and mean), resource summary, the bundle, the gzip run log.

## Jobs

- States: `queued`, `running`, `succeeded`, `failed`, `cancelled`. Fields: progress 0..1, message,
  started, finished, error.
- Progress: the engine gets an optional `progress(done, total)` callback (called every few hundred
  patients); the optimiser already has a `log` callback and reports step by step.
- Limits (configurable): patients per run (default 50k), seeds per run (5), concurrent jobs
  (workers = CPU count), wall time per job (15 min), document size (1 MB).
- The web app polls `GET /jobs/{j}` once a second. Server-sent events can replace polling later.
- A crash in a worker fails that job only.

## Errors

`422` with the spec 01 problem list for invalid documents; `404` unknown ids; `409` when a version
is immutable or a compare is not like for like; `429` over limits. Every error body:
`{"error": {"code", "message", "problems"?}}`.

## Security (minimum for M7; see spec 07)

- Conditions go through the safe evaluator only (spec 01). No user text reaches `eval`.
- Clients send documents and ids, never file paths.
- One shared access token in a header for the hackathon deployment; per-project isolation by id.
- A JEV URL in a decision policy is called by the server: restrict to an allowlist
  (`JEV_ALLOWED_HOSTS`) so the service cannot be used to probe internal addresses.

## Tests

`tests/test_service_*.py` with FastAPI's test client:
- document round trip; validation problems for each code;
- **the loop**: create project from the Finnish template → run → optimise → apply → rerun →
  compare, with small `n`; asserts the rerun used the same patients;
- cache hit on an identical run; limits; job failure reporting; cancel.

## Build order

1. Skeleton, config, store, templates, `/docs` (M2-3).
2. Projects, world, flowchart versions, validate (M2-4).
3. Job runner and engine progress hook (M2-5).
4. Runs with bundle and decisions export (M2-6).
5. Optimisations and apply (M2-7); decide endpoint (M2-8).
6. End-to-end test and a `curl` walkthrough in `service/README.md` (M2-9, M2-10).

## Open points

- Whether results of old engine versions are kept or invalidated on upgrade (lean: keep, show the
